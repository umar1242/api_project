# Техническое описание проекта

Сетка телеграм-ботов с единой API системой: Админ бот, Серт бот, Регистратор бот, Основной бот, Домашка бот, Материал бот.

---

## 1. Цель документа

Этот документ описывает техническую сторону проекта: какую архитектуру и стек технологий использовать, почему именно такую, как спроектировать API, базу данных и с чего начать разработку. Логика самих ботов подробно описана в отдельном документе (`bot_infrastructure.md`) — здесь эта логика переводится в конкретные технические решения.

---

## 2. Общая архитектура

### 2.1 Тип архитектуры: модульный монолит с единым API-ядром

Для проекта такого размера (6 ботов, но общая бизнес-логика и одна база пользователей) оптимальный выбор — **не микросервисы**, а **модульный монолит**: одно бэкенд-приложение, разделённое на чёткие внутренние модули (домены), которое отдаёт единое REST/GraphQL API, а к нему уже подключаются несколько телеграм-ботов как отдельные тонкие клиенты.

**Почему не микросервисы:**
- микросервисы оправданы, когда команда большая, а нагрузка и масштабирование разных частей системы сильно отличаются. Здесь этого нет — все боты используют одну и ту же базу пользователей, курсов и заданий;
- микросервисы резко увеличивают сложность (сетевые вызовы между сервисами, распределённые транзакции, отдельный деплой для каждого сервиса), а на старте проекта это не даёт выгоды, только замедляет разработку;
- модульный монолит даёт 90% преимуществ микросервисной архитектуры (чёткие границы, независимая логика доменов) без её сложности, а при реальном росте нагрузки отдельные модули (например, Конструктор заданий или Файловый сервис) можно позже вынести в отдельный сервис — архитектура это позволяет, если модули изначально изолированы правильно.

**Почему не 6 отдельных ботов с отдельными базами данных:**
- это прямо противоречит требованию единой API системы из твоего же описания — общие пользователи, курсы, коины, файлы должны быть в одном месте;
- дублирование логики авторизации, дедлайнов и загрузки файлов в шести местах — источник багов и лишней работы.

### 2.2 Схема на уровне компонентов

```
                          ┌────────────────────────┐
                          │   Telegram Bot API      │
                          └───────────┬─────────────┘
        ┌───────────┬─────────────┬──┴───────┬─────────────┬────────────┐
        │            │             │          │             │            │
   Админ бот     Серт бот    Регистратор   Основной      Домашка     Материал
   (клиент)      (клиент)    бот (клиент)  бот (клиент)  бот (клиент) бот (клиент)
        │            │             │          │             │            │
        └────────────┴─────────────┴──────────┴─────────────┴────────────┘
                                    │
                          ┌─────────▼─────────┐
                          │   Единое API-ядро   │
                          │  (Backend, REST)     │
                          ├─────────────────────┤
                          │ Модули:              │
                          │ - Users/Auth         │
                          │ - Courses/Groups      │
                          │ - Assignments Engine  │
                          │ - Gamification        │
                          │ - Files Service       │
                          │ - Scheduler/Queue     │
                          │ - Notifications       │
                          │ - Audit Log           │
                          └─────────┬───────────┘
                                    │
                     ┌──────────────┼──────────────┐
                     │              │              │
               ┌─────▼─────┐  ┌─────▼─────┐  ┌────▼─────┐
               │ PostgreSQL │  │   Redis    │  │  S3/облако│
               │ (основная  │  │ (очередь,  │  │  хранилище│
               │  БД)       │  │  кэш)      │  │  файлов   │
               └────────────┘  └────────────┘  └──────────┘
```

Каждый бот — это тонкий клиент, который обрабатывает Telegram-специфичные вещи (команды, кнопки, мини-аппы), но всю бизнес-логику и данные получает через вызовы к единому API-ядру. Ни один бот не работает напрямую со своей отдельной базой данных.

## 3. Рекомендуемый стек технологий

### 3.1 Backend (API-ядро)

**Рекомендация: Node.js (TypeScript) + NestJS**, как альтернатива — **Python + FastAPI**.

Почему именно так:
- **NestJS** уже даёт модульную структуру "из коробки" (модули, контроллеры, сервисы) — это прямо ложится на архитектуру "модульный монолит", описанную выше. Каждый бизнес-домен (Users, Courses, Assignments, Gamification, Files, Scheduler) становится отдельным Nest-модулем;
- TypeScript даёт строгую типизацию, что критично, когда над одним API работает несколько ботов-клиентов — ошибки в контрактах видно на этапе компиляции, а не в проде;
- **FastAPI** — хорошая альтернатива, если у тебя больше опыта с Python: тоже поддерживает чистую модульность, автогенерацию документации API (Swagger/OpenAPI) и асинхронность, что важно при большом числе одновременных запросов от ботов и мини-аппов.

Выбор между ними — вопрос личного опыта, архитектурно оба варианта равноценно хорошо подходят.

### 3.2 База данных

**PostgreSQL** — основная реляционная СУБД.

Почему:
- у проекта чётко реляционные данные с большим числом связей (пользователь → курс → группа → задание → ответ → балл), это классический случай для реляционной модели, а не NoSQL;
- нужны транзакции (например: создание учётной записи + запись в группу + начисление стартовых коинов должны либо произойти все вместе, либо не произойти вовсе) — PostgreSQL даёт это нативно;
- поддержка JSONB-полей позволяет гибко хранить то, что действительно не нуждается в жёсткой структуре (например, черновики ответов в заданиях, где структура вопроса может отличаться), сохраняя гибкость NoSQL там, где нужно, без ухода от реляционной модели.

**Redis** — для очереди задач и кэша.

Почему нужен отдельно от основной БД:
- вся система дедлайнов и уведомлений (напоминание за 10 минут до урока, автоотправка видео, дедлайн оплаты) — это по сути задачи с отложенным выполнением. Redis + очередь задач (например, BullMQ для Node.js или Celery для Python) — стандартное и проверенное решение для этого;
- кэш часто запрашиваемых данных (например, расписание группы, рейтинг учеников) снижает нагрузку на PostgreSQL.

### 3.3 Хранилище файлов

**S3-совместимое объектное хранилище** (Amazon S3, либо более бюджетные аналоги — Cloudflare R2, Selectel S3, Yandex Object Storage).

Почему не хранить файлы прямо в Telegram или на диске сервера:
- ты сам предусмотрел единый Файловый сервис — это подразумевает, что файлы должны быть адресуемы напрямую (по ссылке/ключу), а не только через file_id Telegram, который может протухать и не универсален для доступа с бэкенда;
- объектное хранилище масштабируется горизонтально без ограничений диска одного сервера и упрощает бэкапы.

Файлы, которые пересылаются автоматически в группу (видео уроков), логично продолжать пересылать через Telegram (используя file_id), но при этом хранить резервную копию/метаданные в объектном хранилище — на случай если file_id истечёт или потребуется восстановление.

### 3.4 Боты и мини-аппы

- **Боты:** библиотека **grammY** (для Node.js/TypeScript) или **aiogram** (для Python) — обе современные, асинхронные, с хорошей поддержкой мини-аппов (Telegram WebApp).
- **Мини-аппы (frontend):** **React + TypeScript**, стилизация — Tailwind CSS. Мини-аппы общаются с API-ядром напрямую через REST, авторизуясь через `initData`, который передаёт Telegram (стандартный способ верификации пользователя в Telegram WebApp).

### 3.5 API

**REST API** с документацией через **OpenAPI/Swagger**.

Почему REST, а не GraphQL:
- у ботов и мини-аппов достаточно предсказуемые, некомплексные запросы данных (получить профиль, получить список заданий группы, отправить ответ) — GraphQL оправдан, когда клиентам нужна гибкая выборка произвольных вложенных данных, здесь в этом нет необходимости;
- REST проще документировать, тестировать и защищать (rate limiting, кэширование на уровне HTTP) — что важно при большом числе ботов-клиентов, стучащихся в одно API;
- Swagger-документация, автоматически генерируемая NestJS/FastAPI, сразу даёт удобный способ тестировать эндпоинты вручную на этапе разработки.

Авторизация между ботами и API-ядром — по внутреннему сервисному токену (боты — доверенные клиенты), а мини-аппы авторизуются через Telegram `initData`, который сервер проверяет по подписи, чтобы исключить подделку пользователя.

### 3.6 Инфраструктура и деплой

- **Docker** для контейнеризации каждого компонента (API-ядро, каждый бот, PostgreSQL, Redis) — упрощает локальную разработку и деплой в одинаковом виде на любом сервере;
- **Docker Compose** для старта — этого достаточно на MVP-этапе, оркестрация через Kubernetes на этом масштабе избыточна и добавит сложности без реальной необходимости;
- **VPS** (например, обычный сервер с 2–4 vCPU и 4–8 GB RAM для старта) — этого достаточно для полноценной работы всей сетки ботов на этапе запуска и первых сотен-тысяч пользователей;
- **CI/CD**: GitHub Actions — автоматический прогон тестов и деплой при пуше в основную ветку.

## 4. Структура базы данных (основные сущности)

Ниже — не полная схема, а ключевые таблицы, отражающие связи между модулями:

- `users` — telegram_id, ФИО, роль (student/curator/admin), контакты, дата регистрации
- `courses` — название, тип (платный/бесплатный), описание, план
- `groups` — привязка к курсу, telegram_chat_id, правила, расписание
- `enrollments` — связь user ↔ group, статус (активен/приостановлен/исключён), дата оплаты/дедлайн
- `assignments` — общая таблица заданий (используется и Серт ботом, и Домашка ботом), с полем `context` (сертификатный тест / домашнее задание), типом (1/2/3), дедлайном, привязкой к group/course
- `assignment_questions` — вопросы внутри задания, тип, правильный ответ, мод (с проверкой / без)
- `submissions` — ответы учеников на задания, статус (черновик/сдано/проверено/просрочено), балл, комментарий проверяющего
- `files` — единая таблица файлов, ключ в объектном хранилище, привязка к сущности (assignment/submission/material/enrollment)
- `materials` — учебные материалы, привязка к уроку/группе, тип, дата открытия доступа
- `coins_transactions` — журнал начислений/списаний коинов, причина, привязка к user
- `scheduled_jobs` — задачи планировщика (напоминания, автоотправка, дедлайны)
- `audit_log` — журнал административных действий

## 5. С чего начать: этапы разработки

Разработку стоит вести не "по ботам", а **по общим модулям снизу вверх** — сначала фундамент, потом боты, которые на нём стоят. Это прямое следствие архитектуры "единое API-ядро + тонкие клиенты": если начать с ботов, придётся потом переписывать логику под общее API.

### Этап 0 — Подготовка (1–2 недели)
- настроить репозиторий, CI/CD, окружение (Docker Compose с PostgreSQL, Redis);
- спроектировать и создать первую версию схемы базы данных;
- настроить каркас API-ядра (NestJS/FastAPI) с базовыми модулями-заглушками.

### Этап 1 — Users & Auth + Админ бот-скелет (2–3 недели)
- модуль пользователей и ролей;
- базовая авторизация ботов к API и мини-аппов через Telegram initData;
- Админ бот — минимальный, без бизнес-функций, просто как проверка связки "бот → API → база".

Это первый этап специально выбран так, потому что **все остальные боты зависят от системы пользователей** — без неё нельзя тестировать вообще ничего остального.

### Этап 2 — Регистратор бот + Courses/Groups модуль (2–3 недели)
- создание курсов и групп из админ бота;
- анкета и регистрация пользователя;
- создание учётной записи и enrollment.

Выбран вторым, потому что это точка входа пользователя в систему — без него нет пользователей для остальных ботов.

### Этап 3 — Основной бот (базовая версия, без геймификации) (2 недели)
- личный кабинет, расписание, интеграция с уже созданными группами;
- автоотправка видео/файлов по расписанию — первая интеграция с планировщиком задач (Scheduler).

### Этап 4 — Конструктор заданий (общий модуль) + Серт бот (3–4 недели)
Это самый объёмный модуль, поэтому его стоит делать один раз как общий сервис, сразу проектируя так, чтобы он подошёл и Домашка боту:
- создание заданий трёх типов, черновики, дедлайны;
- математическая клавиатура в мини-аппе;
- проверка ответов, начисление баллов.

### Этап 5 — Домашка бот (1–2 недели)
Поскольку Конструктор заданий уже готов на предыдущем этапе, Домашка бот в основном сводится к дополнительному UI-слою (привязка к урокам, комментарии куратора, интеграция со штрафами) — если бы этот бот делался раньше Серт бота, пришлось бы потом дублировать логику.

### Этап 6 — Материал бот (1–2 недели)
- модуль материалов, привязка к урокам, условия видимости, интеграция с Файловым сервисом.

### Этап 7 — Геймификация полностью + рейтинг + магазин коинов (2 недели)
Геймификация специально вынесена на поздний этап, потому что она **накладывается поверх** уже работающих событий (посещение, сдача домашки, результат теста) — если делать её раньше, чем сами события, начислять будет ещё нечего, а логику придётся тестировать искусственно.

### Этап 8 — Роли куратора, аудит-лог, агрегированные уведомления (2 недели)
Финальные "горизонтальные" улучшения, которые затрагивают все модули сразу — их логично делать в конце, когда основные сущности уже стабильны.

**Итого ориентировочно: 4–5 месяцев** на полный цикл до рабочей версии всей сетки при разработке одним-двумя разработчиками. Если нужно быстрее, можно сократить до MVP — например, Этапы 0–4 (Users, Регистратор, Основной без геймификации, Серт бот) уже дают работоспособный продукт для первого потока учеников, а Домашка, Материал и полную геймификацию можно доразработать после запуска.

## 6. Почему такая архитектура лучше альтернатив (итог)

| Альтернатива | Почему не подходит |
|---|---|
| 6 независимых ботов с отдельными базами | Дублирование логики авторизации, дедлайнов, файлов; нарушает требование "единая API система"; сложно поддерживать |
| Полноценные микросервисы с самого начала | Избыточная сложность для команды малого/среднего размера; распределённые транзакции там, где нужна простая согласованность данных |
| NoSQL как основная БД | Данные проекта существенно реляционные (пользователь-курс-группа-задание-ответ), нужны транзакции и целостность связей |
| GraphQL вместо REST | Запросы клиентов предсказуемы и некомплексны, REST проще защищать и документировать при таком числе клиентов-ботов |
| Kubernetes с самого старта | Ненужный операционный оверхед на этапе, когда хватает Docker Compose и одного сервера |

Модульный монолит с единым API-ядром даёт: одну точку правды для данных, переиспользуемые модули (особенно Конструктор заданий и Файловый сервис), более простой деплой и поддержку, и при этом сохраняет возможность выделить любой модуль в отдельный сервис в будущем, если нагрузка это потребует — архитектура не создаёт технического долга, который помешает росту.
